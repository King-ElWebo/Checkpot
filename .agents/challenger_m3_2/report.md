## Challenges

### [Low] Challenge 1: WebP Magic-Byte Offset Boundary on Abbreviated RIFF Buffers
- **Assumption Challenged:** `verifyImageFile()` assumes any RIFF file whose initial 12 bytes end with `57454250` (`WEBP`) is a valid WebP image.
- **Attack Scenario:** An attacker uploads a synthetic 8-byte file with bytes `52 49 46 46 57 45 42 50` (`RIFFWEBP`), omitting the standard 4-byte little-endian chunk size between `RIFF` and `WEBP`. In `verifyImageFile()`, `file.slice(0, 12)` reads 8 bytes; `arr12` hex representation ends with `57454250`, causing the function to classify the truncated file as `"webp"`.
- **Blast Radius:** None in terms of remote code execution or privilege escalation. The file is assigned a secure random UUID with `.webp` extension and stored in R2 with `Content-Type: image/webp`. The browser will fail to decode it as a valid image and display the alt text.
- **Mitigation (Informational):** For maximum format rigor in future iterations, check `arr12.length >= 12 && webpHeader.startsWith("52494646") && webpHeader.slice(16, 24) === "57454250"`.
- **Status:** Evaluated & Deemed Non-Critical.

### [Low] Challenge 2: Malformed URL Handling in `extractStorageKey`
- **Assumption Challenged:** `extractStorageKey(keyOrUrl)` assumes non-empty inputs starting with `http://` or `https://` can be parsed as valid WHATWG URLs.
- **Attack Scenario:** If passed a malformed protocol string like `"https://"` with no host or path, `new URL("https://")` throws a `TypeError: Invalid URL`. The `catch` block executes `trimmed.replace(/^\/+/, "")`, returning `"https://"`.
- **Blast Radius:** None in application flows. `extractStorageKey` is only invoked on keys generated by `uploadFile` (e.g., `media/<uuid>.<ext>`) or existing URLs in the database (`https://media.checkpot.at/...` or `https://*.public.blob.vercel-storage.com/...`). It does not accept arbitrary external query parameters.
- **Status:** Verified Safe.

### [Info] Challenge 3: Path Traversal Neutralization via Secure UUID Generation
- **Assumption Challenged:** Can an attacker manipulate `file.name` to perform directory traversal (e.g. `../../etc/passwd` or `shell.php.png`) in the R2 bucket?
- **Empirical Proof:** In `src/app/admin/media/actions.ts:62-65`, destination key generation is:
  ```ts
  const secureFilename = `${crypto.randomUUID()}.${ext}`;
  const key = `media/${secureFilename}`;
  ```
  `file.name` is completely discarded for storage key construction. The extension `ext` is strictly derived from the verified binary magic bytes (`png`, `jpg`, or `webp`). Path traversal via filename is mathematically impossible.
- **Status:** Robust & Verified.
